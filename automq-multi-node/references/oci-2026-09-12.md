## `SignatureDoesNotMatch` after a successful list probe

The first create failed before dispatching any VM. Native backend bootstrap
reported readiness, but the published library's legacy-state `GetObject`
prerequisite returned `SignatureDoesNotMatch`. A later probe using the same
credentials and signing region returned `NoSuchKey` for the same key.

That missing-key response proved the request authenticated and the specific
object was absent. The earlier signature failure did not prove absence.
The native journal remained absent in both observations. See
[compute-prerequisite-readiness.json](https://github.com/getcolors/automq-oci/blob/ee2789daa1738b33563488b9294940179234ea09/evidence/2026-09-12/compute-prerequisite-readiness.json) and [converge-attempts.json](https://github.com/getcolors/automq-oci/blob/ee2789daa1738b33563488b9294940179234ea09/evidence/2026-09-12/converge-attempts.json).

A successful list operation does not establish that `GetObject` can
authenticate. A readiness gate must exercise the operations the next stage
requires, including authenticated reads of both existing and missing objects.
Preserve the generated credential across retries instead of issuing a new
one when only one operation has started working.

## Adoption fails after the ops precondition gate passes

The second create completed compute and managed storage, then
`automq-store adopt` failed while reading a `colors-ready` marker with
`GetObject`. OCI again returned `SignatureDoesNotMatch`, even though the
preceding storage precondition gate had passed. That gate exercised
conditional operations in the ops bucket; it did not establish read readiness
for both application buckets and both existing and missing object paths.

No broker had started or formatted its metadata. Genesis remained
uninitialized, and the already-generated secret bundle was retained.
Retry must preserve that bundle and confirm the current genesis records.
An authentication failure before adoption is not evidence that credentials
must be regenerated or that a formatted cluster needs recovery.

For readiness, require exact synthetic write/read comparison and an
authenticated missing-object response in both data and ops buckets, alongside
the conditional-write checks. Retry the complete gate within a bounded window;
a prior successful request does not guarantee the next operation is ready.

## UFW is inactive while raw INPUT rules reject Kafka traffic

All three fresh hosts reported `Status: inactive` from UFW. Their raw rules
still contained:

```
-A INPUT -p tcp -m state --state NEW -m tcp --dport 22 -j ACCEPT
-A INPUT -j REJECT --reject-with icmp-host-prohibited
```

ICMP, established connections and loopback traffic had earlier accept rules.
No accept rule admitted new Kafka client, controller or inter-broker TCP
connections before the terminal rejection. See
[firewall-before-bootstrap.json](https://github.com/getcolors/automq-oci/blob/ee2789daa1738b33563488b9294940179234ea09/evidence/2026-09-12/firewall-before-bootstrap.json).

Checking UFW alone misses this filter. Inspect the effective iptables or
nftables rules and test TCP between peers. Preserve OCI's `InstanceServices`
rules for link-local services. Permit the required Kafka ports before the
rejection with the intended client and private-network source restrictions;
do not flush the firewall. A persistence check must verify the rules survive
the mechanism the image uses to restore them.

These pre-bootstrap observations identified the host filtering. The later
reboot audit below shows why preserving its persistent rules matters.

## Failed readiness probes leave objects that block adoption

The third create passed authentication but refused adoption because two failed
precondition attempts had left synthetic objects in the ops bucket. The
operator checked their exact names and bodies, removed only those two objects,
and verified the bucket was empty. No ownership or genesis marker was changed.
See [precondition-leftovers.json](https://github.com/getcolors/automq-oci/blob/ee2789daa1738b33563488b9294940179234ea09/evidence/2026-09-12/precondition-leftovers.json).

A cleanup block in one process cannot guarantee deletion if its cleanup request
also fails. The correction records each exact probe key before writing and
retains that record across retries until cleanup succeeds. Gate success must
include cleanup of those recorded objects. Do not broadly empty a bucket to
repair a readiness probe; unrelated objects might be application data.

## Literal IP endpoints fail a reverse-DNS prerequisite

The fourth create passed host convergence. Public acceptance reported 13
passes and three failures. Each failed check required `getent` to resolve a
literal broker IP before testing its certificate. Missing reverse DNS caused
the script to skip explicit TLS checks. See [acceptance-attempt4.txt](https://github.com/getcolors/automq-oci/blob/ee2789daa1738b33563488b9294940179234ea09/evidence/2026-09-12/acceptance-attempt4.txt).

An IP SAN certificate does not require a PTR record. A literal IP endpoint
must reach certificate verification directly, with the deployment CA and IP
identity check enabled. DNS names still require forward resolution and name
verification. The failed run remains a failed acceptance run; correcting the
script does not retroactively prove the certificate checks it skipped.

## Zero-second recovery measured after graceful stop is not crash evidence

That acceptance run stopped its victim with graceful `docker stop` and began
timing after the command returned. Its zero-second result excludes the stop
interval and does not measure an abrupt crash.

A crash gate must start its clock before the fault, use an abrupt stop, and
prove the targeted victim remains stopped throughout the survival and recovery
checks. Otherwise a restart policy could restore the victim before the test
has established another broker can serve the partition. A disposable
container probe verified the relevant Docker behavior without touching broker
data. See [docker-semantics.json](https://github.com/getcolors/automq-oci/blob/ee2789daa1738b33563488b9294940179234ea09/evidence/2026-09-12/docker-semantics.json).

Target the victim from the live partition leadership map, verify the pre-fault
produce, and read the exact acknowledged records after the fault. Record both
the fault method and the timing boundary beside any recovery number. The
consumer-offset placement limitation in `acceptance.md` remains unchanged.

## Installing UFW removes the image's native firewall persistence

A real reboot of node 1 exposed a second firewall defect. AutoMQ's owned chain
returned, but the original INPUT and FORWARD rejections and InstanceServices
OUTPUT rules did not. The base package transaction at `08:23:32 UTC` had
removed `iptables-persistent` and `netfilter-persistent` when installing UFW.
See [reboot-node-1.json](https://github.com/getcolors/automq-oci/blob/ee2789daa1738b33563488b9294940179234ea09/evidence/2026-09-12/reboot-node-1.json).

An owned chain surviving reboot does not prove the platform firewall survived.
Preserve the image's persistence mechanism and compare both owned and unowned
rules after a real reboot. The broker remained healthy and the separate
50-record continuity topic survived, but that application success did not make
the failed firewall audit pass.

After native persistence was repaired on all three hosts, node 1 underwent a
second real reboot. All eight audit checks passed: the boot ID changed on the
same instance, the firewall service stayed enabled and active, the owned INPUT
jump remained first, the exact owned and platform rules survived, the broker
was healthy, and both peers could connect to its private Kafka ports. See
[reboot-node-1-after-persistence-repair.json](https://github.com/getcolors/automq-oci/blob/ee2789daa1738b33563488b9294940179234ea09/evidence/2026-09-12/reboot-node-1-after-persistence-repair.json).

The independent 50-record topic again matched SHA-256
`89318d21439ae3cd649c431298c26a01507796ba3ceb7a70966e0d78daa0215e`.
See [continuity-after-repaired-reboot.json](https://github.com/getcolors/automq-oci/blob/ee2789daa1738b33563488b9294940179234ea09/evidence/2026-09-12/continuity-after-repaired-reboot.json). This establishes the repaired
reboot behavior, separately from the earlier failed audit and from full

The repair was published in AutoMQ source
`5aac5a3dfc689071156f5e67c5f1bb7eaec5ca50`, with launcher publication
`c3492fd3627091ad3c07a321061689454534fced` and colors-compute

## Repeated firewall applies append a duplicate UDP rule

The firewall helper compared text from `iptables-save` with its original
argument string. iptables inserted the implicit `-m udp` match when storing
the NTP rule, so the string comparison missed the existing equivalent rule.
Each apply appended another UDP port 123 rule.

The correction asks iptables whether the rule exists with `iptables -C`, which
uses rule semantics rather than formatting. The operator removed only exact
duplicates, retained the first rule and preserved the remaining rule sequence.
See [firewall-ntp-deduplicated.json](https://github.com/getcolors/automq-oci/blob/ee2789daa1738b33563488b9294940179234ea09/evidence/2026-09-12/firewall-ntp-deduplicated.json). The repeated helper must produce no change
before idempotency is claimed. This formatting defect did not invalidate the
two earlier public acceptance runs, but those runs alone could not reveal
that the firewall changed on every converge.
